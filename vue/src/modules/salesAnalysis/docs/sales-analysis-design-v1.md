# 销售分析 V1 设计

## 1. 产品目标

销售分析不是普通的销售额排行榜。老板进入页面后，应在一个工作区内依次回答三个问题：

1. 当前配送商品的销售金额主要分布在哪些大类；
2. 哪些客户贡献主要销售额，他们使用商品的广度如何；
3. 选定某个商品后，哪些客户正在使用，哪些客户最重要。

V1 不展示毛利、采购成本或库存成本。现有成本字段和采购写入销售字段存在历史主权风险，不能在没有完整成本追溯和异常标记前发布毛利结论。

## 2. 页面信息结构

### 2.1 顶部范围和概览

- 默认统计近 30 天，提供近 7 天、近 30 天、近 90 天和自定义日期，单次范围最多 90 天；
- 概览显示销售金额、使用客户数、成交商品数和销售数量结构；
- 销售数量不能把不同单位强行合成一个数字。主单位显示最大数量单位，同时提示“另有 N 种交易单位”，详情中按单位展开。

### 2.2 大类总览

- 主图使用矩形树图：矩形面积表示大类销售金额，直接标注金额占比、客户数、商品数和主要数量单位；
- 点击大类同时更新右侧客户贡献排行和下方小类/商品工作区；
- 大类颜色只表达选中和层级，不使用多彩色制造虚假的业务等级；
- 无有效金额的分类进入“无有效销售额”，不参与金额占比。

### 2.3 客户总览

- 大类总览右侧使用横向条形图显示选中范围或选中大类的客户销售额 Top 5；
- 每个客户同时保留销售金额、金额占比、使用大类数和商品数，正式页面可点击进入客户中心对应客户；
- 客户按父客户 `nx_DO_department_father_id` 去重，内部子部门不重复算作多家客户。

### 2.4 小类和商品

- 选中大类后，左侧使用小类列表，显示销售金额、金额占比、按单位汇总的数量、客户数和商品数；
- 右侧商品表显示商品、销售数量、销售金额、加权平均单价、使用客户数和前两位重要客户；
- 商品表的商品名称前显示缩略图，右侧客户抽屉顶部显示同一商品大图；两处共用服务端返回的配送图、父类图和平台图字段，不允许各自拼接不同图片来源；
- 商品默认按销售金额降序，可在正式实现中切换为销售数量或客户覆盖，不在 V1 首屏增加更多排行榜；
- 点击商品行或行尾箭头后，从页面右侧打开客户分布抽屉；客户详情不得放在长表格底部；
- 抽屉顶部显示商品销售额、客户数、数量和加权平均单价，下方逐家显示客户销售金额、贡献占比、销售数量、加权平均单价、订货日数和最近成交日期。
- 商品图片只用于识别具体商品，不参与大类、小类面积、金额排行或任何统计计算。

## 3. 指标口径

### 3.1 事实范围

- 唯一事实表：`nx_department_order_history`；
- 组织范围：Owner Token 对应配送商，服务端从可信身份得到 `distributerId`；
- 时间字段：默认按实际到货/配送日期 `nx_DO_arrive_date` 统计，页面明确显示统计日期范围；
- 当前 `nx_department_orders` 中未完成订单不进入分析；
- 无商品 ID、无客户父部门 ID、金额为空或不可转换的数据保留在数据质量计数中，不静默归到任意商品或客户。

### 3.2 销售金额

```text
销售金额 = SUM(valid_decimal(nx_DO_subtotal))
```

- `nx_DO_subtotal` 是历史成交销售行金额；
- 客户商品当前订货价、商品建议价、库存标价和采购金额都不是销售事实；
- 退款、退货和售后冲销目前未形成统一净额事实时，V1 标注为“成交销售额”，不命名为“净销售额”；后续接入销售退货冲销后再升级口径。

### 3.3 销售数量

```text
有效销售数量 = 有效实际配送/计价数量，否则回退到有效订货数量
数量键 = 商品 ID + 交易单位
```

- 优先读取能代表实际交付的 `nx_DO_weight`/计价重量及其单位；缺失时兼容 `nx_DO_quantity + nx_DO_standard`；
- 数量必须大于 0 且可转为数字；
- 斤、公斤、箱、个、瓶等先按原交易单位分别汇总；没有可靠换算快照时禁止跨单位相加；
- 同一商品存在多种单位时，商品行分行或显示多个单位段，不输出一个伪总量。

### 3.4 平均单价

```text
同商品同单位加权平均单价 = 同范围有效销售金额 / 同范围有效销售数量
```

- 不使用 `AVG(nx_DO_price)`，避免不同订单数量权重相同导致失真；
- 只在金额与数量可以归到同一交易单位时计算；
- 分类级平均价也按单位分别计算，例如 `¥5.31/斤 · ¥18.20/箱`，不产生跨单位平均价。

### 3.5 客户和重要客户

- 使用客户：统计范围内对目标分类或商品至少存在一条有效历史成交行的父客户；
- 重要客户：目标商品内按客户销售金额降序；
- 每位重要客户显示：销售金额、商品金额贡献占比、同单位数量、加权平均单价、订单日数、最近成交日期；
- 商品详情抽屉单次最多返回 200 家客户并逐家展示；极端情况下超过上限的客户显示“其余 N 家合计”，避免大响应拖慢桌面端；
- V1 不自动给客户贴高低价值标签，避免把短期金额误写成永久客户等级。

## 4. 分类归属

- 页面业务层级固定为大类 → 小类 → 商品；
- 优先使用历史订单保存的配送商品/分类快照字段；快照不足时按 `nx_DO_dis_goods_id` 关联配送商品，再关联 `nx_distributer_father_goods`；
- 当前配送目录中 level 0 为大类，其下一级为页面小类，商品通过 `nx_dg_dfg_goods_grand_id` / `nx_dg_dfg_goods_father_id` 关联；正式 SQL 必须以生产真实层级数据验证，不能只凭字段命名猜层级；
- 历史期内商品被改分类时，如果历史没有完整分类快照，V1 按当前目录归类并返回 `CURRENT_CATALOG_FALLBACK` 数据质量标记，不能宣称是历史原始分类。

## 5. 正式接口

所有接口经 Electron 主进程只读白名单和桌面安全会话访问，由服务端 Principal 限定配送商范围。页面不得提交配送商 ID。

### 5.1 页面概览

`GET /api/desktop-dispatch/v1/sales-analysis/overview?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD`

返回：

- 总销售金额、客户数、商品数；
- 按单位汇总的销售数量；
- 大类分布；
- 全局客户 Top 5；
- 数据质量计数。

### 5.2 大类下钻

`GET /api/desktop-dispatch/v1/sales-analysis/categories/{categoryId}?startDate=...&endDate=...`

返回选中大类的小类列表、商品列表、大类客户 Top 5。

### 5.3 商品客户

`GET /api/desktop-dispatch/v1/sales-analysis/products/{goodsId}/customers?startDate=...&endDate=...&limit=200`

返回指定商品的使用客户总数、按销售额排序的客户明细（单次最多 200 家）、其余客户合计和单位分组。

## 6. 服务端结构

新功能是跨订单、商品目录和 B2B 客户的只读经营投影，不属于销售助手的拜访/报价子域。建议使用：

```text
com.nongxinle.distribute.analytics.sales
├── api
├── application
├── domain
└── persistence
```

- API 只调用 Application，并要求 `analytics:sales:read`；
- Application 负责范围校验、查询编排和读模型组装；
- Application 内部读模型固定单位分组、加权平均价、客户贡献和数据质量规则；后续规则扩大时再独立拆出 Domain；
- Persistence 只读历史订单、配送商品目录和 Department 客户；
- 新类不得放入历史顶层 `controller/service/dao/entity/dto/utils`；新 Mapper package 接入前必须补 MyBatis 扫描与启动测试。

## 7. 桌面端结构

```text
vue/src/modules/salesAnalysis
├── api
├── components
├── presentation
├── views
├── docs
├── routes.js
├── index.js
└── README.md
```

- 路由：`/sales-analysis`；
- 路由名：`SalesAnalysis`；
- 模块权限：`salesAnalysis`；
- 侧边栏新增“经营分析”分组，放在“AI 助手”和“系统管理”之间；
- 所有金额、数量、平均价和客户排行在 presentation 层保持相同口径，组件不自行重算业务规则。

## 8. V1 验收重点

1. 改变时间范围后，概览、大类、小类、商品和客户排行使用完全相同的日期边界；
2. 当前未完成订单不会提前进入销售分析；
3. 不同单位不会被合成一个数量或一个平均单价；
4. 平均单价使用金额除以数量的加权口径；
5. 父客户去重正确，子部门不会重复放大客户数；
6. 商品重要客户金额合计与商品销售金额守恒，Top 5 加其余客户等于商品总额；
7. 大类金额合计与总销售金额守恒，小类合计与所属大类守恒；
8. 跨配送商资源 ID 被拒绝，Owner Token 失效时不能读取报表；
9. 空数据、非法数字、缺商品和缺客户数据都有明确状态或质量计数；
10. 正式实现同步更新本模块 README 和变更日志，记录数据口径、接口、测试和界面验收。
